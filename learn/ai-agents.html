AI agents: how a model plans, uses tools and acts.

A chatbot answers. An agent pursues a goal: it decides what to do next, asks for tools to be run, reads the results and keeps going. See exactly how that works, then step into the agent's shoes.

  • About 30 minutes
  • Intermediate
  • No account required
  • Original diagrams

From answering to acting

An AI agent is a language model placed in a loop. At each turn it decides what to do next: answer, or ask for a tool to look up the rota, search documents or draft a message. Your program runs the tool, adds the result to the conversation, and asks the model again. The loop continues until the goal is met or a person needs to step in.

Goal→Model decides→Program runs tool→Result added↺Answer

Not everything needs an agent

You can give a model more or less control over a task. More control lets it adapt to unexpected results, but also makes its behaviour harder to predict. Start with the simplest approach that works.

    Which pattern fits?

    Key ideas to take away

    • Your program controls which actions run. A tool call is a structured request. Code decides whether it runs. Enforce permissions and approval checks in code as well as describing them in the prompt.
    • Tool results are data, never instructions. Text inside a document, email or web page can try to hijack an agent (prompt injection). Follow the application's instruction hierarchy and permissions. Retrieved content cannot grant new permissions or override those instructions.
    • Use tools to check facts, and ask when information is missing. Good agents use tools for facts and ask people when information is missing.
    • Keep people in the loop for anything consequential: sending, deleting, paying, or decisions about individuals.
    • Use the lowest rung of autonomy that works. A fixed workflow is easier to test and trust than a free-roaming agent.

    What a real tool definition looks like

    Most model APIs accept tools as JSON Schema. The description matters: it's how the model decides when to use the tool.

    {
  "name": "get_rota",
  "description": "Return the volunteers available on a given day, with any notes on their record.",
  "input_schema": {
    "type": "object",
    "properties": { "day": { "type": "string", "description": "Day of the week, e.g. Saturday" } },
    "required": ["day"]
  }
}

    A simplified agent loop

    This pseudocode omits provider-specific message formats, schema validation, permissions, error handling and approval records. Implement those controls before using it with real tools. Approval should cover the exact action and arguments.

    NEEDS_APPROVAL = {"send_message"}

def run_agent(goal, llm, tools, max_steps=8):
    messages = [{"role": "user", "content": goal}]
    for _ in range(max_steps):                      # always cap the loop
        reply = llm(messages, tools=tools)
        messages.append(reply)
        if not reply.tool_calls:
            return reply.text                       # final answer
        for call in reply.tool_calls:
            if call.name in NEEDS_APPROVAL and not ask_person_to_approve(call):
                result = "Not approved by a person."
            else:
                result = tools[call.name](**call.arguments)
            messages.append({"role": "tool", "tool_call_id": call.id, "content": str(result)})
    return "Step limit reached. A person needs to take over."

    This reason–act–observe cycle is often called ReAct, after Yao et al. (2022), “ReAct: Synergizing Reasoning and Acting in Language Models” ↗(opens in a new tab).

    Memory

    Short-term memory
    The conversation available to the model, limited by the context window (Lesson 03). Long runs need summarising or trimming.
    Long-term memory
    Notes stored outside the model and retrieved when relevant, usually with the same techniques as RAG (Lesson 05).

    Connecting tools: MCP

    The Model Context Protocol is an open standard for connecting models to tools and data, so a tool written once can be used by many applications (Gullí, Chapter 10).

    Defending against prompt injection

    • Give each agent the least access it needs; an agent that can't read the donor list can't leak it.
    • Require approval for actions that send data out or can't be undone.
    • Clearly separate instructions from retrieved content in the prompt, and tell the model that content is untrusted.
    • Test with adversarial examples, like the one in the lab, before going live (Lesson 07).
